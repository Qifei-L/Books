## 1 目标与本轮边界

Books 的目标是建立可靠、可追溯的记账后端，让科目定义、交易记录和会计查询使用一致的业务规则。本轮先确认需求，再选择会计引擎、设计接口并开发；不把技术方案当成已经批准的业务规则。

项目仓库为 Qifei-L/Books，本稿编写时尚无实现代码。当前范围是后端需求定义，暂不包含 Web。本文中的 MVP、默认规则、性能目标及阶段安排均为建议，待需求审阅确认；文档发布不代表需求已批准。

| 层级 | 建议边界 |
| --- | --- |
| 本次详细需求 | 科目查询、创建与维护、启停、权限、审计，以及余额与流水的业务口径。 |
| 后端基础范围 | 账套边界、科目、平衡记账、凭证关联、基础账务查询及操作追踪。先明确依赖，不承诺同一批完成全部模块。 |
| 暂不纳入 | Web、完整 ERP、库存与工资、税务申报、自动银行对账、复杂审批、集团合并及自动报表制度转换。 |

### 如何衡量第一阶段成功

业务人员能够建立并维护一份可用科目表；每个科目的名称、编码、类型和状态有清楚含义。未经授权或不符合规则的操作被拒绝，历史账务不会因科目维护而消失或被悄悄改写。

有有效记账数据后，科目余额与流水能互相核对，并能与总账保持一致。如果第一批仅交付科目主数据，应明确标示余额与流水尚未启用，不能以假零余额冒充完整记账能力。

### 需要确定的五组业务选择

A. 首期是否面向多个独立公司；需要哪些币种与业务时区。
B. 科目编码是否可自定义，名称是否允许重复。
C. 只需平面分组，还是必须有父子科目及末级记账。
D. 使用后的类型、编码和名称可否修改。
E. 停用能否保留非零余额，由谁批准及恢复。

后文给出推荐默认值与可验证案例。未确认的默认值不等于用户批准；会计引擎和具体技术选型放在需求确认之后。

## 2 账套与科目的业务定义

### 公司与账套边界

账套是独立会计记录的边界。一个科目、凭证及余额必须明确属于某一账套；不同账套的相同编码可以存在，但任何查询或操作不得混用它们。首期是否支持同时管理多个公司待确认。建议先完成一个账套的完整流程，不等同于已经决定永远只支持单公司。

每个账套需确定本位币、会计年度起止、业务时区及适用的报表口径。当前未指定币种，不预设 USD、人民币或其他币种。建议首期不做外币重估和汇兑损益；是否需要外币交易应在引擎选型前决定。

### 科目最少应表达的信息

| 信息 | 业务含义与建议 |
| --- | --- |
| 稳定身份 | 系统识别同一科目；改名称或编码不应改变历史凭证关联。 |
| 编码 | 业务人员使用的识别码。建议必填、账套内唯一，支持字母和数字组合，不以编码推断会计类型。 |
| 名称与说明 | 名称表达用途，说明补充使用边界。建议保留用户确认的文字及大小写；长度限制在接口设计阶段明确。 |
| 会计类型 | 至少能区分资产、负债、权益、收入、费用；银行、往来等特殊用途如需额外约束，另行定义。 |
| 分组 | 用于整理和查询；建议首期为可选平面分组，不改变会计类型或余额计算。 |
| 状态 | 启用或停用；历史记录始终保留。 |
| 系统用途 | 如后台流程确需专用科目，明确用途与保护规则；不预先指定名称为 Suspense 的科目。 |

### 分组与父子科目不是同一需求

平面分组用于把科目放在一起查看；父子科目还涉及父项汇总、移动子项、是否允许父项直接记账。建议首期只做平面科目表，分组可后置；若必须采用树形结构，建议只允许末级科目记账，并在开发前补充层级与汇总验收。

会计类型决定核算和报表归类，不应被随意替换的分组标签代替。具体类型清单及报表映射须经业务确认，不由尚未选定的引擎反向决定需求。

## 3 科目主数据功能需求

| 编号 | 功能 | 必须满足的业务结果 |
| --- | --- | --- |
| COA-01 | 查询与详情 | 按编码、名称搜索，按类型及状态筛选；结果可分页、顺序稳定，能识别停用科目。详情展示完整维护信息。 |
| COA-02 | 创建 | 校验必填及重复规则；失败不留下半条记录。反复提交同一次创建操作，不得意外生成重复科目。 |
| COA-03 | 编码维护 | 建议允许自定义编码和有记录的改码；账套内唯一，停用科目的编码仍不可被其他科目占用。 |
| COA-04 | 名称与说明 | 建议允许修改并保留历史变更记录；修改不改变已记账金额和凭证关联。 |
| COA-05 | 会计类型 | 创建时选择合法类型；建议未使用时可在校验后修改，使用后禁止直接改类型。 |
| COA-06 | 分组 | 若纳入首期，只提供可选平面分组及筛选；改分组不影响金额、借贷方向或凭证关联。 |

### 建议的重复判断

编码忽略首尾空格及英文大小写判断重复，但具体展示形式由统一规则确定。名称建议同账套内不重复，至少忽略首尾空格及英文大小写，避免“Bank”和“ bank ”产生难以区分的科目。若业务确需同名，必须要求编码明确区分，并在审阅中改定该规则。

### 使用后的修改边界

“已使用”指科目已经出现在有效会计记录中，包括期初余额或已过账凭证；草稿引用也需在修改前检查。建议已使用科目仍可改码、改名和改说明，但不能直接改会计类型、归属账套或稳定身份。

如已使用科目的类型确实错误，提出专门更正方案，经审阅后处理相关凭证及报表影响，不能用普通编辑操作悄悄改历史归类。删除和合并不进入首期。

### 明确的成功与失败示例

同一账套已有 EXP-01，新增“ exp-01 ”应提示编码重复且不创建记录；改名“办公费用”为“办公室费用”后，原凭证仍属于同一科目，余额不变；已经存在期初余额的科目改为另一会计类型，应被拒绝。

## 4 生命周期 权限与追踪

### 启用与停用

启用科目可用于符合规则的新交易。停用后不可新增记账或被自动记账流程继续使用，但仍可查看历史凭证、余额、流水和报表。停用不是删除，也不是把余额清零。

推荐首期采用谨慎规则：只有余额为零、没有未结单据或待处理事项、没有未来已过账记录的普通科目才可停用。净余额为零但有两笔尚未处理的相反方向事项，也不能直接停用。是否允许带余额停用由用户确认。

恢复启用须记录原因。需要更正停用科目的历史交易时，建议先由有权限者恢复，再按正常更正流程执行；不设置不留记录的“强制使用”。系统专用科目是否允许停用，必须由对应业务流程明确定义。

### 建议权限分工

| 角色能力 | 建议权限 |
| --- | --- |
| 查询者 | 查看其授权账套内的科目及账务信息，不可维护。 |
| 记账维护者 | 创建科目、改编码/名称/说明，办理已授权记账操作。 |
| 管理者 | 在维护权限基础上，批准停用和恢复、处理需要审阅的例外。 |
| 系统流程 | 仅使用明确授权的账套和科目；不能绕过启停或会计校验。 |

这是能力划分，不预设最终角色名称。多公司如纳入范围，应逐账套授权；有一个公司的权限，不代表可以看到或操作其他公司。

### 每次变更都能解释

应能够回答谁、何时、对哪个账套和科目、做了什么、前后内容是什么，以及需要时的原因。用户不能通过普通科目编辑删除审计记录。操作失败不应留下“已成功修改”的错误记录。

两人同时编辑同一科目时，后提交者不能无提示覆盖先提交者。停用与记账同时发生时，应保证一个明确结果：记账先成功则重新检验能否停用；停用先成功则拒绝新的记账，不出现部分成功。

## 5 余额 流水与质量底线

### 账务查询的业务口径

余额按账套的会计日期计算，明确截止日及币种。金额保留业务要求的精度，借贷方向可解释，不把数值负号直接当作错误。存在未来交易时，查询历史日期不得包含未来金额。

流水应至少给出期间、期初余额、日期、凭证关联、摘要、借方发生、贷方发生、逐笔余额与期末余额。区间首尾是否包含必须明确；建议包含所选两端会计日。没有期间流水时，期末应等于期初，而不是自动显示零。

建议期末＝期初＋借方发生－贷方发生，采用借方为正的核对口径，并明确展示方式。分页只改变展示范围，不改变整个期间的期初、发生额或期末；后页运行余额应承接前页。

### 完整性与安全

| 要求 | 验收底线 |
| --- | --- |
| 平衡与一致性 | 正常记账不得产生不平衡凭证；科目维护不得直接修改余额。失败操作整体撤销，不留下孤立明细。 |
| 历史保护 | 不静默删除、合并或重写历史；停用科目仍计入相关历史报表。更正有明确流程和来源。 |
| 访问边界 | 未登录、无权限、跨账套访问及伪造管理操作均被拒绝；不在错误信息中暴露机密数据。 |
| 可恢复性 | 发布前验证备份可恢复；结构变更有回退或补救方案，不能以回滚覆盖新产生的真实交易。 |
| 可理解性 | 错误指出业务原因和可行下一步；不把缺数据、未启用功能或失败查询伪装为零余额。 |
| 可操作性 | 服务故障和关键操作可追踪；金额、日期及权限行为有自动化测试。 |

### 数据规模与响应要求

建议设计阶段先以单账套 1,000 个科目、10 万条记账明细作为验证样例，再根据实际规模调整。普通科目查询建议目标为常规测试负载下 95% 请求在 2 秒内返回；余额与长期间流水单独测量，不承诺未经测试的性能。测试环境、并发量和测量方法在技术方案中约定。

本节描述业务结果，不指定数据库、引擎、算法、接口路径或存储结构。

## 6 分阶段验收与开发流程

### 建议 MVP 与后续安排

| 阶段 | 交付与退出条件 |
| --- | --- |
| MVP A 科目主数据 | 完成 COA-01 至 COA-05、基本权限、启停状态及审计；先确定账套、编码和类型规则。启停可验证主数据状态，但余额、未结事项和未来交易的停用检查依赖 MVP B；未实现时不得声称这些条件已验证通过，也不得据此开放真实账务停用。没有账务数据时不声称余额/流水已完成。 |
| MVP B 最小记账闭环 | 依赖平衡凭证、期初及期间规则，提供真实余额与流水；通过金额和历史一致性验收。可与 A 连续开发，但单独验收。 |
| 后续另审 | 平面分组、CSV 导入导出、父子科目、其他业务单据和更复杂报表。多公司及外币是否首期必需仍由决策 A 确定，未决定前不排除也不承诺；确属首期必需时，先调整范围再开发。 |

### 首批必须通过的业务场景

1. 重复编码和重复创建不会生成多份科目；失败创建没有残留。
2. 改码、改名不改变科目身份、既有凭证及金额；已使用科目不能直接改类型。
3. 停用后的新记账被拒绝，旧流水仍可查询；不满足停用条件时给出原因。
4. 无权限人员不能维护；两人并发修改不会无提示相互覆盖。
5. 期初借方 100，期间借方 30、贷方 20，期末为 110；没有发生额时仍为 100。
6. 同一流水查询分页前后总额不变，截止日之后的交易不进入历史余额。

### 标准开发流程及确认关口

需求审阅：确认本稿范围、业务规则和验收案例，记录未决项。关口一是用户确认需求，而不是开始写代码后再补定义。

技术设计：对照已确认需求选择并验证引擎，设计领域模型、接口、安全、数据迁移及测试方案。关口二是审阅技术方案，关键限制先反馈，不能偷偷删减需求。

分支开发：按小任务实施并写自动化测试；通过代码审查后合并。集成验证应使用明确的测试账套，不以正式账务数据随意试写。

业务验收与发布：逐条运行验收场景，记录缺陷并修复；发布前确认目标环境、备份与回退方案。关口三是验收通过并取得所需发布授权。发布后检查关键读写和账务一致性。
